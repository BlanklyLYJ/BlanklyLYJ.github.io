## 一、UI 框架:必考模块

### 1. UI 框架的核心结构

面试官最爱问"你的 UI 框架是怎么搭的"。我的回答骨架是五层结构:

| 层级 | 职责 | 关键点 |
|---|---|---|
| `UIModule` | 总入口,管理所有界面实例与层级 | 为每个层级分配 sortOrder 范围 |
| `UIBaseLayer` | 单个层级管理器 | 排序、显隐、层级跳转 |
| `UINode` | 中间层,连接 Prefab 与脚本 | 加载、卸载、池化 |
| `UIBaseView` | 业务基类,处理交互 | 各界面按需继承 |
| `UITemplate` | 模板底板 | 自带 Canvas + GraphicRaycaster |

打开界面通过唯一 key 拉配置,再走加载 → 实例化 → 入场动效 → 显示的流水线。

### 2. UI 优化清单

| 优化点 | 做法 |
|---|---|
| 动静分离 | 同图集、同深度、不重叠时才能合批;静态与动态 Canvas 分离 |
| 图集 | 同界面的散图打到一个 Atlas,减少 SetTexture |
| Raycast | 关闭无点击需求的 Image 的 Raycast Target |
| Rebuild 控制 | Layout/Material/Vertices 任一变化都触发重建,少用 Outline |
| 入池 | UI 模板复用,避免反复 Instantiate |
| 隔帧加载 | 大界面拆分到多帧加载,先用模板占位 |
| Animator | 不用时移出屏幕或禁用组件,避免 `Animator.Initialize` 抖动 |
| CanvasGroup | 隐藏界面时设 alpha=0 + 移出屏幕,而非 SetActive(false) |

### 3. Mask vs RectMask2D

| 维度 | Mask | RectMask2D |
|---|---|---|
| 实现 | 模板测试 + Sprite mask | 矩形裁剪(Cull) |
| 性能 | 较差,增加 draw call | 较好,矩形直接剪裁 |
| 适用 | 不规则形状 | 滚动列表、矩形遮罩 |

### 4. UI 弧形/无限列表

通过 `ScrollRect` 的 `normalizedPosition` 算偏移,只渲染可见区域的子节点。关键点:

- 提前计算每个子节点的目标位置(弧形参数方程)
- 入池的子节点复用,通过 SetSiblingIndex 重新排序
- 与动效配合时,被 Animator 控制的子节点要小心坐标被锁住

## 二、战斗框架:从帧同步到 DOTS

### 1. 帧同步 vs 状态同步

| 维度 | 帧同步 | 状态同步 |
|---|---|---|
| 传输内容 | 玩家操作指令 | 单位状态快照 |
| 服务端 | 转发指令 | 模拟战斗,广播结果 |
| 客户端 | 自己模拟 | 直接表现 |
| 一致性要求 | 极高,需定点数 | 低,允许偏差 |
| 网络流量 | 小 | 大 |
| 反作弊 | 难 | 易 |
| 适用 | RTA、格斗、机甲(飞弹多) | MMORPG、SLG |

机甲类游戏因为有大量实时飞弹表现,适合帧同步;MMO 适合状态同步。

### 2. 帧同步的关键问题

- **逻辑/表现分离**:逻辑层用定点数,表现层做插值与平滑
- **预测回滚**:预测超过阈值必须停止,只回滚到最近确认帧
- **随机数**:必须用确定性随机,种子同步

### 3. DOTS 三件套

| 组件 | 角色 |
|---|---|
| ECS | 实体-组件-系统,内存连续存放,Cache 命中率高 |
| JobSystem | 多核并行,使用 `NativeContainer`,通过 `ReadOnly`/`WriteOnly` 标注保证安全 |
| Burst | 基于 LLVM 编译为原生码,只支持值类型 |

ECS 内存按 16KB chunk 分配,相同 archetype 的实体紧密排列,这是性能提升的根源。

### 4. 战斗 AI 优化

经典场景题:**1 万只怪、3 座塔、每塔每秒攻击 5 次,怎么优化?**

我的思路是分层:

1. **空间划分**:四叉树 / 八叉树 / 网格,只检索攻击范围内的怪
2. **优先队列**:每塔维护一个最小堆,跟踪血量最低单位,O(log n)
3. **分帧**:攻击 CD 内分摊计算,每次只处理 1/n 单位
4. **JobSystem 并行**:多塔并行
5. **CD 期间预判**:算出哪些单位会在下次攻击前离开范围,直接忽略
6. **平方距离**:不开方,牺牲一点精度换性能
7. **ComputeShader**:把可见性判断扔到 GPU(主程研究过,自己没敢提)

### 5. AI 设计模式对比

| 模式 | 优点 | 缺点 |
|---|---|---|
| 有限状态机 (FSM) | 简单直观 | 状态多时爆炸 |
| 行为树 (BT) | 模块化、可复用 | 节点开销 |
| HTN(任务网络) | 任务链清晰 | 影响因素多时不稳定 |
| GOAP(目标导向) | 智能、有想象力 | A* 难调、性能消耗大、需量化条件 |

## 三、性能优化:面试官的"压测题"

### 1. 性能排查思路

```
Profiler → 找到耗时函数
 ├─ CPU:Gfx.WaitForPresent 长 ⇒ GPU 瓶颈
 ├─ GC.Alloc 多 ⇒ 装箱、字符串、new
 └─ Rebuild 频繁 ⇒ UI 层级/动效问题
```

### 2. 内存与 GC

- C# GC:Mark-Compact 标记压缩
- 装箱触发场景:接口接收值类型、`ArrayList`、字符串拼接、`yield return 0`(用 `null` 代替)
- 对象池泄漏:武器挂在角色上忘了卸,角色销毁时 ab 包还在引用 → 引用计数 + 定期巡检

### 3. DrawCall 优化

| 批处理 | 触发条件 |
|---|---|
| 静态批处理 | 静态物体 + 同材质 |
| 动态批处理 | 顶点数 < 300 + 同材质 + 同光照 |
| SRP Batcher | URP/HDRP + 同 Shader |
| GPU Instancing | 同 Mesh + 同 Material(支持参数) |

## 四、C# 与 Lua 基础题速查

### C# 高频

- **class vs struct**:堆/栈、引用/值、`struct` 含 class 引用字段时仍在栈上,引用字段指向堆
- **string 不可变**:`a="abc"; a="111"` 创建新字符串并改引用,频繁拼接用 `StringBuilder`
- **Dictionary 底层**:数组 + hash 链表(拉链法)
- **List 底层**:数组,扩容 2 倍
- **虚函数表**:每个有虚函数的类一张表,运行时按类型查表派发
- **async/await 状态机**:编译器生成状态机,`await` 后的代码是回调续体

### Lua 高频

- **继承**:metatable `__index` 指向父类,`setmetatable(child, {__index = parent})`
- **table 底层**:数组分段 + 哈希表,根据 key 类型自动选择
- **__index vs __newindex**:`__index` 读拦截,`__newindex` 写拦截
- **xLua 交互**:C# 对象在 Lua 端是 userdata,通过对象索引保持联系;xLua 维护 `__mode="v"` 弱引用表,GC 时回调 C#

## 五、面试流程与软技能

### 投递清单

按顺序投了:鹰角、蛮啾、米哈游、西山居(解限机)、散爆、点点、莉莉丝、网易、雷火、巨人、叠纸、库洛、心动、网龙、沐瞳、灵犀……

实际进面的:西山居(技术一二面 + HR)、散爆(技术一二三面 + HR)、点点(SLG 项目,HR + 技术 + 制作人面)。

### 高频软问题

1. **自我介绍**:背景 + 项目经历 + 当前方向 + 未来规划
2. **离职原因**:职业发展、城市、项目方向,避免抱怨前公司
3. **职业规划**:从业务深入到框架,再到主程方向
4. **加班看法**:能接受结果导向,但不能纯堆工时
5. **反问**:工作流程、团队规模、项目阶段、扩展空间

### 反思与建议

- **简历准备**:JD 每条要点都对应到自己项目里能讲清楚的模块,优先准备"框架 + 优化"两个故事
- **项目深度**:框架题答得越深,后续问题越简单
- **手撕代码**:链表(奇偶重排、判环)、二叉树(遍历)、堆(TopK)、快排、二分、状态机模拟,基础不熟就翻车
- **不会就承认**:虚函数表编译期实现、BSP 树这些深问,直接说"了解概念但没深挖"比硬答强
