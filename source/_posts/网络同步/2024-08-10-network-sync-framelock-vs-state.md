## 一、同步方案的历史演进

网络同步方案不是一天设计出来的,大致经历了这几个阶段:

1. **指令同步(早期 RTT 游戏)**:客户端只上传操作,服务端广播,所有表现各算各的,极易作弊且不一致
2. **状态同步(MMORPG 时代)**:服务端跑完整逻辑,把"权威状态"广播给客户端,客户端只做表现
3. **帧同步(LOCKSTEP,RTS/MOBA 时代)**:服务端只转发操作指令,所有客户端按相同顺序、相同输入跑相同逻辑,保证结果一致
4. **混合同步(现代)**:关键状态权威 + 表现层帧同步 / 客户端预测 + 服务端回滚

每一种都是对前一种痛点的回应:指令同步太作弊 → 状态同步太重 → 帧同步卡顿 → 预测回滚补丁。

## 二、状态同步:服务端权威

核心思想:**服务端跑一份完整的游戏世界,客户端只是显示终端**。

```
客户端 A 操作 ──▶ 服务端(模拟) ──▶ 广播状态变化
                                      │
客户端 B 接收 ──▶ 插值表现 ◀────────────┘
```

### 优势

- 防作弊强:客户端没有逻辑,改了也没用
- 断线重连简单:服务端 push 全量状态即可
- 适合持久化世界(MMORPG):服务端就是数据库

### 劣势

- 服务端压力大:每个怪、每个 buff 都要 tick
- 开发复杂:逻辑要写得"无副作用",才能反复模拟
- 网络流量大:N 个玩家 × M 个属性 = 大量快照

### MMORPG 状态同步的预测与回滚

直接广播状态会有明显延迟(操作 → 服务端 → 广播 → 表现),常见优化是**客户端先行 + 服务端回滚**:

1. **客户端预测**:玩家按下移动,客户端立刻把角色向前挪一格,不等服务端确认
2. **指令队列**:每条指令打上序号 + 服务端时间戳,放进有序队列
3. **服务端权威**:服务端跑真实逻辑,把结果回包给客户端
4. **回滚重放**:客户端收到服务端结果后,如果与本地预测不一致,把队列里未确认的指令重新跑一遍

```csharp
// 伪代码
struct InputCmd {
    uint seq;          // 指令唯一 id
    uint serverTime;   // 服务端时间点
    InputData input;
}

Queue<InputCmd> pending = new();

void OnLocalInput(InputData i) {
    var cmd = new InputCmd { seq = nextSeq++, input = i };
    pending.Enqueue(cmd);
    ApplyInput(predicted, i);   // 客户端立即预测
    SendToServer(cmd);
}

void OnServerSnapshot(Snapshot snap, uint ackSeq) {
    // 把已确认的从队列里出
    while (pending.Count > 0 && pending.Peek().seq <= ackSeq)
        pending.Dequeue();
    // 用服务端快照覆盖本地
    CopyFrom(predicted, snap);
    // 重放未确认的指令
    foreach (var c in pending) ApplyInput(predicted, c.input);
}
```

### 跳过表现的特殊情况

某些关键延迟下,逻辑必须"跳过死亡演出"。比如玩家被杀后又复活继续受伤,此时本地表现上要跳过死亡取出角色逻辑(因为玩家并未出局),但播报照常发。这种数据冲突要把"逻辑状态"和"演出状态"分开维护。

## 三、帧同步(LOCKSTEP):指令广播

核心思想:**服务端不跑逻辑,只负责把所有客户端的操作按固定节奏转发给所有人**。每个客户端拿到同一份操作流,跑相同的逻辑代码,理论上得到完全相同的结果。

```
Tick 1:  A 上传"按下↑" | B 上传"按下空格"
              ▼
         服务端打包成 Frame{1, [↑, 空格]}
              ▼
   A、B、C... 收到后各自 simulate(Frame)
```

### 优势

- 服务端轻量:只转发,不模拟,可以做得很便宜
- 流量小:每帧只广播操作字节,不广播整个世界状态
- 一致性强:只要逻辑确定,所有端必然收敛
- 适合大量同屏单位(RTS、MOBA)

### 劣势

- 对抗确定性要求极高:浮点、迭代顺序、随机数、物理全部要严格确定
- 一卡全卡:任何一个客户端延迟,所有玩家都得等
- 反作弊弱:服务端不验逻辑,只能靠事后录像校验
- 重连困难:必须从断线那帧开始 replay 所有操作

## 四、王者荣耀:逻辑帧与渲染分离

王者是帧同步的标杆实现,关键设计是**逻辑帧率与渲染帧率解耦**。

### 为什么必须分离

帧同步要求逻辑严格确定性,逻辑帧率固定(比如 30 逻辑帧 / 秒)。但渲染走的是 Unity 主循环,60 / 90 / 120 显示帧率都可能。如果逻辑直接绑渲染 Update,高刷新率手机会跑得过快,慢机又会卡死。

### 分离方案

- **逻辑层(LogicFrame)**:固定 30 Hz,纯 CPU 计算,无渲染。所有战斗判定、伤害、位移都在这里发生
- **渲染层(RenderFrame)**:60+ Hz,根据逻辑层最近状态做**插值**,让画面看起来丝滑
- **输入层(InputFrame)**:玩家操作打包成指令,上传服务端,等服务端下发再喂给逻辑层

```
玩家输入 → 服务端 Frame Buffer → 逻辑帧(20/30 Hz) → 插值 → 渲染帧(60+ Hz)
```

### 关键技术点

| 技术点 | 说明 |
|---|---|
| 定点数 / 整数运算 | 浮点数跨平台不确定,统一用 FixedInt / FixedPoint |
| 确定性容器 | 不能用 Dictionary(遍历顺序不定),用有序结构 |
| 确定性随机 | 用种子 + LCG,跨平台一致 |
| 物理引擎 | Unity PhysX 不可用,要自研确定性物理 |
| 帧追赶 | 网络抖动后,把积压的帧一次性跑完追上 |
| 渲染插值 | 在两个逻辑帧之间用 t∈[0,1] 做线性 / 球面插值 |

### 逻辑帧代码骨架

```csharp
public class FrameSimulator
{
    private Queue<FrameInput> _inputQueue = new();
    private int _logicFrame;   // 当前逻辑帧号

    public void PushFrame(FrameInput input) => _inputQueue.Enqueue(input);

    // 固定间隔调用
    public void Tick(float deltaTime)
    {
        // 累积时间,够一个逻辑帧就跑一次
        _accumulator += deltaTime;
        float logicInterval = 1f / 30f;   // 30 逻辑帧
        while (_accumulator >= logicInterval)
        {
            _accumulator -= logicInterval;
            if (_inputQueue.Count == 0) break;   // 等服务端
            var input = _inputQueue.Dequeue();
            ApplyInput(input);
            Simulate(logicInterval);
            _logicFrame++;
        }
    }

    void ApplyInput(FrameInput i) { /* ... */ }
    void Simulate(float dt) { /* 确定性模拟 */ }
}
```

### 渲染插值

```csharp
// 渲染层
public class RenderEntity : MonoBehaviour
{
    public Vector3 prevPos;   // 上一逻辑帧位置
    public Vector3 curPos;    // 当前逻辑帧位置
    public float t;           // 两个逻辑帧之间的插值

    void Update()
    {
        transform.position = Vector3.Lerp(prevPos, curPos, t);
    }
}
```

这样即使逻辑只有 30 Hz,渲染跑 60 / 120 Hz 也能丝滑。

## 五、明日方舟:帧对齐机制

方舟严格说不是同步问题(单机塔防),但它把"帧对齐"做到了极致,值得借鉴。

### 30 帧对齐

方舟本质是**帧游戏**:1 倍速下 1 秒 = 30 帧(30 f),所有动作(攻击、技能、动画)都以帧为单位结算。

以安洁莉娜二技能(精一)为例:

```
攻速加成 3,攻击间隔缩短 *0.15
理论攻击间隔 = 100 × (1.9 × 0.15) / (100 + 3) = 0.277s = 8.30f
```

帧不存在小数,8.30f 实际表现是 8f, 9f, 8f, 8f, 9f...(用整数帧补偿小数部分,长期平均趋近 8.30)

精二后攻速加成变成 7:

```
攻击间隔 = 0.266s = 7.99f ≈ 8f
```

此时变成了 8f, 8f, 8f...(恒定),DPS 比精一高了约 4.30%(约 838 点法伤)。**看似只差 1 点攻速,实际差了一档**。

### 帧对齐对代理(自动战斗)的影响

方舟的代理只记录时间轴:**第几秒放干员、第几秒开技能**,机械回放。问题在于:

- 手机掉帧后,实际帧 ≠ 显示帧,某些"该发生的动作"卡没了
- 二倍速下从 30 f/s 提到 60 f/s,手机压力翻倍,更容易掉
- 如果掉的是能天使过载、银灰真银斩、艾雅法拉火山这种高倍率技能的伤害帧,击杀节奏就被破坏
- 累积起来 → 出怪时间轴 vs 操作时间轴错位 → 代理失败

### 解决方案

- 治本:换高性能手机 / 模拟器
- 治标:减少撤离操作,减少对决战技能的依赖,多用自动触发技能

## 六、对比表

| 维度 | 帧同步 | 状态同步 |
|---|---|---|
| 服务端职责 | 转发指令 | 模拟世界 |
| 客户端职责 | 跑完整逻辑 | 表现 + 预测 |
| 一致性来源 | 确定性逻辑 | 服务端权威 |
| 流量 | 小(只传指令) | 大(传状态) |
| 反作弊 | 弱(录像校验) | 强(逻辑闭环) |
| 重连 | 难(replay 全部帧) | 易(快照即可) |
| 断线影响 | 一卡全卡 | 只影响自己 |
| 代表游戏 | 王者、星际、LOL | WoW、原神、MMORPG |

## 七、选型建议

```
单位多(几十上百)、需要强一致性、可接受确定性约束 → 帧同步
单位少、需要持久化世界、需要强反作弊           → 状态同步
断线频繁 / 网络差                                → 状态同步(帧同步卡起来很难受)
单机需要"录像回放"功能                           → 帧同步(本质就是录像)
混合方案:战斗帧同步 + 大厅状态同步              → 王者荣耀的做法
```
