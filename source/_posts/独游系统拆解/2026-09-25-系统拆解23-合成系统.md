## 一、定位:表驱动的配方合成

合成系统的设计身份:一个**通用底座**,烹饪只是它的一个站点类别。配置表(H_合成表,27 条配方)承载全部配方数据,CraftSystem 只做校验与结算——**加新配方 = 加表行,零代码**。

这个系统是"数据与逻辑分离"纪律的展示窗:系统代码只认识"配方=材料表+产出+失败产物+站点"这个抽象,不认识"烤咸肉"或"铁剑"。所有具体配方知识都在表里。

## 二、核心规则

### 2.1 校验链(顺序固定)

```
配方在表里存在?
→ Station 匹配?(请求里带的合成台类型 vs 配方要求的站点——防面板外伪造跨站请求)
→ 材料齐备?(同材料多行聚合判定——表里两行都要 1 个草药,合起来要 2 个)
→ 扣材料 → 成功率 roll(85%)
   成功 → 产出入包(×max(1, ResultCount))
   失败 → 失败产物入包(×1)
→ 产出入包失败(背包满)→ 退还全部材料(不吞资产)
```

四道守卫各有来历:表存在(防脏 Id)、Station 匹配(防跨站伪造——用篝火面板的请求触发锻造配方)、材料聚合(表的表达力)、退还(背包满不吞料)。

### 2.2 失败产物生态

| 类别 | 失败产物 | 说明 |
|------|---------|------|
| 烹饪 | 残渣 2072 | 可卖 |
| 药剂 | 未知药水 2073 | 喝了有随机效果 |
| 熔炼 | 矿渣 2074 | 可卖 |
| 锻造 | 粗制装备(各槽位一件) | 属性残次但能穿 |

**失败不没收材料价值**——惩罚是机会成本,不是资产毁灭。失败产物甚至有正面价值(未知药水的赌博感、粗制装备的前期过渡),把合成失败从"纯损失"改写成"次优结果"。

### 2.3 站点分段(表内 ID 段)

篝火 1-7 / 厨房 101-103 / 半成品 201-204 / 手工 301 / 药剂 401-403 / 熔炼 501-503 / 锻造 601-802。系统本身支持任意 Station——**接新站点 = 放一个交互物 + 挂面板,零系统改动**;<mark>当前只接了篝火(烹饪面板),其余站点等载体(厨房=玛尔塔面包房等地图内容)</mark>。

| 项 | 数值 |

## 四、系统关联

**上游**:配置表 TBRecipe(Materials/MatCounts/Result/FailResult,$Item[] 跨表引用保证 Id 可靠)、背包(材料与产出的通道)、交互系统(站点入口)。
**下游**:烹饪(复用本系统,见第 2 篇)、<mark>M3 锻造台 crafted 词缀(词缀系统联动)</mark>。
**联动**:掉落(材料来源)、商人(失败产物残值的回收)。

## 五、设计取舍记录

**取舍一:成功率全类别统一 85%**。按配方分级成功率(简单 95%/高级 60%)更拟真,但"成功率"在 M1 是未调参的占位值——统一 85% 让失败体验一致,调参等各站点的实际手感数据。<mark>分级成功率随 M2 站点扩展重新评估</mark>。

**取舍二:当帧结算,无进度演出**。合成进度条(站在台前搅拌 3 秒)有仪式感但阻塞操作节奏;M1 全部当帧结算+音效,连续合成的节奏由玩家自控。<mark>进度演出在"需要节流的合成"(锻造)落地时再加</mark>。

**取舍三:聚合判定而非逐行判定**。表允许同一材料出现多行(表达"或"与"且"的混合),系统先聚合再判定——表的表达力优先,系统多做一步归并。这条换来配方表不用强行归一(策划填表自由)。
