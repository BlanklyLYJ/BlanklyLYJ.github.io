## 一、定位:Service 层 UI 体系

一个先声夺人的架构判断:**UI 不 ECS 化**。UI 强依赖 Canvas/RectTransform/协程/动画,硬套 ECS(纯数据组件+系统遍历)收益低成本高——UI 留在传统 OOP 的 Service 层,与 ECS 玩法层通过事件通信。**架构原则是工具适配问题,不是信仰问题**。

## 二、核心规则

### 2.1 五层结构

```
UIFunction(3) → UIGuide(4) → UITips(5) → UISystem(6) → UIPool(10)
功能面板         引导层       提示层      系统级       缓存池
```

层数即渲染顺序与遮挡语义:功能面板在最下,系统级(加载屏)在最上——**开面板时声明层,遮挡关系自动成立**,不需要每个面板自己管 sortingOrder。

### 2.2 生命周期

```
Init → Start → Show → Hide → Reset
```

单例界面(同 Key 只存在一份,重复打开置顶)/多例界面(列表项类);反射创建(面板类与 prefab 按约定绑定,注册表驱动);**隔帧关闭栈**(同帧多次关闭请求排队到下一帧处理——防关闭中再关闭的重入)。

### 2.3 面板池

UIFrame.Pool(UI GameObject 的 Get/Return 已集成开关闭环);LoopScrollView(虚拟滚动列表)共用此池——**UI 对象池一处建,两类消费方共享**(见对象池体系的 UI/Gameplay 双池分工)。

### 2.4 现有面板清单

标题/登录/大厅/设置/存档位/加载/游戏主界面(HUD)/背包/游戏菜单 + **运行时构建的对话/商店/营火/技能/装备面板**——后一批不走 prefab,代码构建 UI。

## 三、全运行时构建路线(既定)

对话/商店/营火等 gameplay 面板全部代码运行时构建(ShopPanelView 同模式)——这条路线的依据与代价:

- **依据**:零 prefab 维护(改 UI 不进 Unity 编辑器)、prefab 与代码的引用漂移风险归零、批量修改是代码重构(工具齐全);
- **代价**:视觉调优效率低于编辑器拖拽;
- **实际权衡在小地图调研时再次验证**:插件集成成本吃回一半收益的判断,就是基于"本项目 UI 全运行时构建"这个前提。

**预制体规范**(少量 prefab 面板遵守的纪律):根节点不挂组件;背景独立子节点(大图 RawImage/小图 Image);命名前缀 btn>txt>img>rawimg——**规范服务于代码查找**(transform.Find("btnXxx") 的约定俗成)。

## 四、系统关联

**上游**:GameLaunch(初始化)、各 Controller(面板逻辑)。
**扇出**:全部 UI 面板、LoopScrollView、PoolManager(UI 池)。
**联动**:输入系统(面板的上下文压栈——开店压 UI 上下文,关店还原);面板范式三件套(开面板压上下文/ESC 关闭链/玩家销毁强关)。

## 五、设计取舍记录

**取舍一:UI 留 OOP 不进 ECS**——上文,工具适配判断。

**取舍二:反射创建而非手工注册**。手工注册(每个面板在启动代码里 new 一份)显式但每加面板改一处;反射创建(约定优于配置:Key→类名→类型查找)零维护。代价是改名时要守约定(Key 与类名一致)——约定检查可以工具化(命名校验器已有先例)。

**取舍三:隔帧关闭栈**。同帧关 A 时 A 的关闭回调里又请求关 B——直接递归关闭在 UI 动画/协程语境下是崩溃源;排队下一帧,串行安全。
