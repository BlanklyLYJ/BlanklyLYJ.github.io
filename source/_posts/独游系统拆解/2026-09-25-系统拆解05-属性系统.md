> 「游戏系统拆解」系列第五篇(样板批完结篇),拆属性系统(GameplayAttribute)。它是养成域的地基,也是全项目的数值中枢——战斗公式、装备词缀、食物 Buff、技能增益、世界魔力浓度、天气强度,全在它身上取值。设计对标 UE 的 GAS(Gameplay Ability System)属性半边,核心理念一句话:**属性只是记录,玩法来取值**。

<!-- more -->

## 一、定位:一套机制服务所有数值

先看这个系统诞生的直接动机:旧属性体系(五维:力量/敏捷/体质/智力/魅力)**从未被赋值,恒为 0**。于是全项目的战斗公式长期空转——攻击恒等于 5,防御恒等于 0,任何装备加成、状态效果都改变不了什么。数值空转的系统比没有系统更糟:它假装自己在工作。

重建时的关键判断不是"把五维改成六维",而是换范式:

| 旧范式 | 新范式 |
|--------|--------|
| 属性 = 角色身上的一个组件字段 | 属性 = 全局注册表里的注册项,任何实体挂组件即拥有 |
| 五维写死在代码里(属性类型与默认值都是代码) | 点分层级字符串 + FNV-1a hash,先登记再使用 |
| 修改器直接改数值 | Base/Current 分离,修改器参与结算 |

"任何实体都是宿主"带来的表达力跃迁:

```
Character.Stats.Phy          ← 角色六维·体魄(战斗公式取)
World.Magic.AmbientLevel     ← 世界·环境魔力浓度(全局单例,随天数演化)
Weather.Rain.Intensity       ← 天气·降雨强度(天气系统写入,条件引擎读)
Weapon.Prof.Sword            ← 武器熟练度·剑
```

一个系统的四种用途:角色的、世界的、天气的、武器的。如果各建各的(角色属性组件/世界状态字段/天气参数/熟练度字典),就是四套增删改查、四套存档、四套事件——现在是一套。**数值中枢的意思不是"它很大",而是"改一处公式,处处生效;加一种数值,零新基建"**。

与 GameplayTag 系统同构(点分层级 + hash 缓存比较)是刻意为之:设计师只需要记一套命名心智。

## 二、核心规则全拆

### 2.1 属性标识与注册纪律

属性 ID 是点分层级字符串,比较走 FNV-1a hash 缓存。**先登记再使用**:所有属性必须在注册表登记(含 Min/Max/Default),未注册的 hash 读写被拒绝并警告。

这条纪律和 WorldState 的"未注册变量拒绝写入"同源:字符串 ID 的拼写错误是数据类 bug 的第一大来源,**让拼错在第一次读写时就炸,而不是埋进存档里三周后才被发现**。

### 2.2 初始值从哪来:角色卡桥接(半接通状态,如实记录)

注册表定义的是"属性类型"(名字/上下限/默认值),**角色个体的六维初始值不在代码里,在角色卡上**——这是设计定死的口径:

- 角色卡是 ScriptableObject 资产(`CharacterCardData`:CardId/六维各 1-20/倾向标签/好感特例),卡库编辑器可改,**卡是数据权威**;
- 实体创建时按 CardId 绑卡(`EntityFactory.BindCard` → 卡库懒解析 → `CardAttributeBridge.ApplyStats`):先 InitDefault 补缺席项,再 SetBase 用卡值覆盖——所以绑卡实体的六维 = 卡面值;
- **实体属性是创建时快照**:改卡后需重建实体才生效(实时同步属角色成长域的长线设计);
- 绑卡但卡库解析不到(卡名写错/加载失败)时仍铺默认六维——保持"绑卡实体属性集必有六维条目"不变式;
- MaxHP 特意不走卡:血量上限归创建参数所有,"六维推导血量"的公式等角色养成侧定稿再接。

**当前接通面(截至写作时)**:同伴(Viktor/Hassan)已绑卡,六维真实来自角色卡;**玩家实体尚未绑卡**——创建参数里没传 CardId,六维走注册表默认值(全 10),这是一笔已登记的债(玩家主角卡 + 选人界面是后续批次);另有配置表版的 11 旅人初始数据(TBTravelerInit,含六维/初始装备/初始物品)已建表但**尚未接线**——SO 卡与配置表谁是数据权威需要一次裁决(倾向:表做内容源喂卡,卡保持运行时权威);卡库加载也只在 Editor 模式可用,打包模式的 AB 管线待接。

### 2.3 Base / Current 分离(本系统的灵魂)

```
Base     持久值:成长、装备的永久加成写这里,进存档
Current  瞬态值:= clamp((Base + ΣAdd) × ΠMul),不进存档,读档重算
```

为什么必须分离?想象不分的后果:装备 +5 力量,直接把力量改了;卸下装备,减回去——**减得回去吗?**期间吃了料理(力 +2,300 秒)、中了虚弱(力 −3,60 秒),这些限时修改器各自到期时要"还原"到什么值?没有 Base 做锚,还原就是玄学。传统 MMO 用"快照+回滚"硬扛,边界情况(到期顺序、叠加规则)全是坑。

Base/Current 分离后语义变得干净:

- **一切永久来源写 Base**(升级、任务奖励);
- **一切临时来源挂修改器**(装备、Buff、食物、技能);
- Current 是纯函数式结算结果——**任何时刻重算都得到同一个值**,不存在"漂移";
- 读档只存 Base,Current 重算——瞬态修改器(食物 Buff 等)随读档清空,与"限时效果不跨会话"的既有口径一致。

### 2.4 三类修改器与结算序

```
AttributeModifier {
    AttrHash;  // 目标属性
    Op;        // Add 加法堆叠 / Multiply 乘法堆叠 / Override 终值覆盖
    Magnitude; // 数值
    Duration;  // 秒;0 = 永久
    SourceId;  // 来源(装备实例/食物/技能),支持整批移除
}

结算顺序:Override(最后一个生效)> Multiply > Add
Current = clamp((Base + ΣAdd) × ΠMul) —— 再被 Override 直接设终值
```

结算序是经典的加法先于乘法(加法吃乘法加成):`Base 10, Add +5, Mul ×1.2` → `(10+5)×1.2 = 18`,而不是 `10×1.2+5 = 17`。这个顺序对玩家是可教学的("百分比加成也算你的白值加成"),对数值策划是可控的(乘区数量决定成长爆炸曲线)。

**SourceId 整批移除**是修改器与来源系统的合同:卸装备按 InstId 一次清掉 5 条词缀修改器、料理到期自动移除、技能增益按技能 Id 撤销。上一篇(烹饪)讲过的"食物槽位 = 修改器 SourceId 段位反查",就是建立在 SourceId 命名空间纪律上的高级用法——**来源系统自己管自己的段位,中枢不感知具体含义**。

Duration > 0 的修改器由属性系统每帧衰减,到期移除并标脏重算。不需要任何来源系统自己计时。

### 2.5 可消耗属性

IsConsumable 标记(如 HP):Current 可被玩法直接消耗(受伤扣的是 Current),clamp 到 [0, Max 所指属性]。**血条是属性系统的一等公民而不是战斗系统的私产**——受伤、回血、上限增长(升级 Base)、上限 Buff(修改器)全部走同一条管线,HUD 订阅 AttributeChangedEvent 即可。

### 2.6 事件

```
AttributeChangedEvent { EntityCreationIndex, AttrHash, OldCurrent, NewCurrent }
```

仅 Current 变化时发布。HUD、剧情条件、级联引擎(规划中:属性 A 变化触发属性 B 重算)统一订阅。一次结算一次事件,不逐修改器刷屏。

## 三、首批属性表与消费方

| 属性 | 范围/默认 | 消费方 |
|------|-----------|--------|
| Character.Stats.Phy/Dex/Per/Wil/Cha/Int | 1-20 / 10 | 攻防公式、ATB 速度、DC 检定、食物 Buff、词缀 |
| Character.Derived.MaxHP | 1-9999 / 100 | HealthComponent 桥接 |
| Character.Derived.MoveSpeed | 0-20 / 5 | MoveComponent 桥接 |
| Weapon.Prof.Sword/Axe/Bow | 0-100 / 0 | 熟练度(预留) |
| World.Magic.AmbientLevel / Phase | 0-100, 0-6 / 0 | 世界魔力七阶段(低魔世界观的主时钟之一) |
| Weather.* | — | 天气门控(条件引擎 weather 源) |

六维取 1-20、默认 10 是跑团(如 D&D 系)的刻度——**刻意压窄的数值区间**。1-9999 式的大数值把设计空间摊薄(每一点无意义),而 1-20 里每一点都该被感知:检定调整值、交易门槛、对话分支,1 点体魄的差异有戏可做。旧五维到新六维的映射:Agility→Dex、Constitution/Strength→Phy、Intelligence→Int,新增 Per(感知,侦查/打听向)与 Wil(意志,信仰/抗性向)。

六维已接的战斗公式:

```
ATB 速度   = Dex × 10 + Phy × 2 + 50
物理攻击   = Phy × 2 + 5
物理防御   = Phy × 1.5
```

默认值 10 下:ATB 速度 170、攻击 25、防御 15——数值终于不空转。**换血时接受数值整体通胀**(旧恒 0 → 新默认 10),这是一次性成本,换来所有公式从此有真实差异。

## 四、玩家体验走查

属性系统玩家永远看不见全貌,但处处摸得到:

1. **吃一份烤咸肉**(烹饪篇的例子):体魄 +2 持续 300 秒。打开六维面板,体魄显示 12(Current)而不是 10(Base)——面板读 Current,鼠标悬停或详情能看到 Base 和修改器来源;
2. **穿上"熊力"词缀的护腕**:体魄再 +N。此时攻击力面板显示的数值变了——因为攻击公式取的是 Current,修改器结算对消费方完全透明;
3. **Buff 到期**:300 秒后体魄自己回到 10,不需要任何"下 Buff"的显式操作——修改器到期、重算、发事件、面板刷新,一条链全自动;
4. **睡觉存档再读档**:体魄还是 10,食物 Buff 没了(限时增益不入档)——玩家理解成"睡了一觉,吃的也消化了",语义自洽;
5. **DC 检定**:劝说商人时骰 `1d20 + Cha 调整值 vs DC`——检定调整值直接取属性 Current,穿了"雄辩"词缀的饰品真的能改变剧情分支的通过率;
6. **世界魔力浓度**:World.Magic.AmbientLevel 随游戏天数演化,推着世界从"低魔"走向"魔力复苏"——玩家在条件门控的剧情里逐渐感知到"最近怪事变多了",背后是同一个属性系统的全局单例在走表。

## 五、系统关联

属性系统是全项目扇入扇出都最广的枢纽,动它之前要查总纲的枢纽扇入表。

**上游(谁写)**:角色卡(创建时六维 Base 快照)、升级成长、装备词缀(ApplyModifier)、食物 Buff、技能增益、世界魔力系统(全局单例按天写)、天气系统。

**下游(谁读)**:战斗公式(ATB/攻防)、DC 检定、条件引擎(attr 源,剧情门控 `Wil ≥ 12`)、HUD 面板、HealthComponent/MoveComponent 桥接(MaxHP/MoveSpeed)。

**明确不在本体系的**:情绪(Mood/Loyalty/Fear)、熟练度旧组件、价格修正(PriceModifier)——这三者保留旧制,边界写死,防止"中枢化"滑向"什么都要塞进来"的过度设计。

## 六、设计取舍记录

**取舍一:"属性只是记录,玩法来取值"——中枢不驱动任何玩法**。诱人的增强方向是给属性挂触发器("力量到 18 时解锁猛击")——否决。中枢一旦有了自己的意志,每个消费方都要防着"属性系统会不会替我做决定"。它只做记录、结算、广播,玩法系统自己来问、自己决定。这条克制是它敢于承接全项目数值的前提——**越是被依赖的底层,越要没有性格**。

**取舍二:读档重算而非快照 Current**。存 Current 省一次结算,但引入"存档时点的瞬态被永久化"的语义污染(存档瞬间恰好在 Buff 里,读档后 Buff 一直在)。重算让"存档 = Base + 空修改器列表 + 世界长期状态"语义最干净,代价只是一次启动结算。

**取舍三:三 Op 而不是自由公式**。修改器只支持 Add/Multiply/Override 三种,不支持"力量的一半加到攻击"式自由表达式。三 Op 覆盖了 99% 的装备/Buff 需求,而自由公式的复杂度(解析、调试、可视化、设计师学习成本)是数量级的跃升。真需要复杂公式的地方(攻击结算),那是消费方公式的事,不是修改器的事——**各层管各层的表达力**。

**取舍四:MaxHP/MoveSpeed 的桥接是半成品,如实记录**。属性表里注册了这两个派生属性,但 HealthComponent.Max 与 MoveComponent.Speed 当前是独立真源——属性修改器改不动它们。这就是烹饪篇里"食物 Buff 禁配 MaxHP/MoveSpeed"的根源。计划在装备管线 M2 统一真源(组件值变为属性的投影),在那之前,半成品状态明确写进边界文档,**"看起来支持但其实无效"的配置项直接禁掉**。
