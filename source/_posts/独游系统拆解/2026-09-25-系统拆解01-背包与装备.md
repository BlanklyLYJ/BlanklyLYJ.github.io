> 这是「游戏系统拆解」系列第一篇。这个系列把我在做的俯视角 RPG《维尔德拉斯传说》里的各个系统,按策划视角逐个拆开:为什么做、玩家体验到什么、数值杠杆在哪、和谁联动。技术实现(spec)不是本系列的重点,设计逻辑才是。第一篇从最不起眼但谁都绕不开的系统开始:背包。

<!-- more -->

## 一、定位:一句话说清这个系统是什么

**背包系统是物品进出的唯一通道**——拾取、穿装、消耗、交易、任务道具发放,全部走同一套增删查与事件。这句话听起来像废话,但它是整条经济链的地基:

- 掉落系统只负责"生成世界里的物品实体",进不进包、能不能进包,是背包说了算;
- 商人系统只负责"算价格",扣钱给货走的是背包的增删;
- 剧情对话里"乞儿拿走你 3 个金币",走的还是背包的通道。

好处是显而易见的:**任何系统的物品变动都会发同一个事件(InventoryChangedEvent),UI、任务、成就只需要订阅一个地方**。如果每个系统自己改玩家的物品列表,背包界面就会变成一个永远刷不对的灾难现场。

## 二、设计目的:为什么背包要"双轨制"

传统 RPG 背包有两种主流做法:

| 方案 | 代表 | 特点 |
|------|------|------|
| 纯堆叠 | 上古卷轴、巫师 3 | itemId → 数量的字典,简单高效 |
| 纯实例 | 暗黑破坏神 2、流放之路 | 每件物品是独立对象,可带词缀 |

纯堆叠的问题在装备词缀面前是致命的:两把"单手长剑",一把带"锐利的(前缀)+攻击力"、一把带"熊力(后缀)+体魄",如果只存 itemId → count,它们就是同一个东西——词缀没地方放。

纯实例的问题则相反:一组 99 个的箭矢、一摞草药,每根箭一个实例对象,纯属浪费。

所以最终采用**双轨制**:

```
背包(InventoryComponent)
├── Items: Dictionary<itemId, count>   ← 非装备走堆叠轨(材料/消耗品/货币)
└── EquipInstances: List<EquipInstance> ← 装备只存实例(词缀随实例走)
```

三条推论自然成立:

1. **同 id 的多件装备互不覆盖**——两把同型号长剑,一把三词缀一把白板,在背包里是两行,卖出时按实例整件卖;
2. **穿戴是标记不是移动**——EquipInstance 有个 Equipped 布尔位,穿上只是打标记,实例不离列表。这样卸下装备时不需要"找回"那个实例,词缀也不会丢;
3. **增删查 API 自动路由**——AddItem/RemoveItem/HasItem 按物品类型判断走哪条轨,调用方完全无感。剧情卡要给玩家一把剑,不需要知道剑是实例制的。

**金币也是一种物品**(配置表里 Id=200 的 Currency 类型,最大堆叠 9999)。这个决定让交易系统零新组件:买药就是"扣 200 号物品 ×N、加 1001 号物品 ×1",和合成系统扣材料加产物是同一段代码。金币的唯一特殊性只在 UI 层——它显示在角标而不是格子里。

## 三、玩家体验走查

从玩家视角把一次完整的"战利品变成战斗力"流程走一遍:

1. **击杀野怪**,掉落物从尸体弹出(0.35s 抛物线),金币是旋转 45° 的菱形小方块,稀有度 ≥3 的装备带一根竖直光柱;
2. **走近,自动磁吸**——2.2m 内掉落物加速飞向玩家,0.5m 内入包,全程无按键。背包满了会有 1.2 秒节流提示,而不是刷屏报错;
3. **打开背包(B 键)**,装备类物品一行一件,行内直接拼出词缀名——"锐利的单手长剑·熊力",不需要 tooltip 悬停才知道自己捡到了什么;
4. **点击装备行,立即穿戴**——槽位自动解析,穿上后该行从背包列表消失(因为穿戴中不占格);同一帧,装备面板(EquipPanel)对应槽位出现拼名与词缀明细;
5. **六维面板/攻击力立刻变化**——装备的词缀走属性修改器(详见属性系统篇),生效是即时的,不需要刷新;
6. **战斗中按 B 想换装?拒绝**——装备面板战斗中不可开启,穿/卸 API 战斗中直接返回失败;
7. **回城卖货**——商人界面里装备实例逐件列出,只允许整件卖"×1",按实例直达本件;卖出的钱进的是金币堆叠轨。

这条链路里玩家从没见过"实例"两个字,但每一步的手感(词缀分明、穿装即时、战斗锁装、按件卖货)背后都是双轨制在支撑。

## 四、核心规则全拆

### 4.1 容量口径:穿戴不占格

容量上限 20 格,口径 = **堆叠条目数 + 未穿戴实例数**。两个刻意的设计:

- **已有物品叠加不受容量限制**——99 个草药占 1 格,第 100 个也不用开新格。容量只卡"新条目",不卡数量增长;
- **穿戴中的装备不占背包格**——穿在身上的 6 件不计入 20 格。否则"换装"会频繁触发容量问题,玩家会被迫为穿装备腾格子,这是纯粹的坏体验。

### 4.2 装备槽位:表内 11 槽映射面板 6 槽

配置表的装备槽位是跑团式的细粒度 11 槽:头/脸/左手/右手/双手/上衣内衬/外衣/下衣内衬/裤腿/脚/手指。而玩家实际操作的面板是 6 大槽:

| 表内槽位(枚举值) | 面板槽位 |
|------------------|---------|
| 头(1)、脸(2) | Head |
| 左手(3)、右手(4)、双手(5) | Weapon |
| 上衣内衬(6)、外衣(7) | Body |
| 下衣内衬(8)、裤腿(9)、脚(10) | Legs |
| 手指(11) | Accessory ×2(两个饰品位取空位) |

映射通过 TBItem.Param1 → 装备表 Slot 解析。这里留了一个**兜底扫描**:如果表数据里 Param1 指向无效(这是已知的表侧数据债),槽位解析失败时按 Weapon→Body→Legs→Head→Acc1→Acc2 顺序找第一个空位,全满则替换 Weapon。兜底的意义是"表错了游戏不炸",表修复后自动回到精确解析。

### 4.3 穿戴流程与属性修正

穿上一件装备,内部发生的事:

```
Equip(实例)
  ├─ 槽位已有装备?→ 先走完整 Unequip 归还旧件
  ├─ EquippedItems[slot] = 实例InstId(注意:存的是实例 Id 不是物品 Id)
  ├─ 逐条词缀 ApplyModifier(Duration=-1 永久, SourceId=实例InstId)
  └─ 发 EquipmentChangedEvent → 背包/装备面板刷新
```

两个细节值得停一下:

- **字典值是 InstId 而非 itemId**。早期版本存 itemId,结果双持两把同 id 匕首时,卸下其中一把会把另一把的属性加成也一并移除(因为移除逻辑按 SourceId=itemId 匹配)。实例化之后 SourceId=InstId,每件装备的属性加成独立可拆——这是实例制改造的直接动机之一;
- **卸下 = 按 SourceId 整批移除**。一件装备 5 条词缀就是 5 个修改器,卸下时一次清干净,不存在残留幽灵加成。

### 4.4 战斗中锁装

战斗中一律拒绝穿/卸(与"技能换装"同口径)。这不是防呆设计,是**防漏洞设计**:如果允许战斗中卸装备,玩家可以在敌人攻击前摇的瞬间卸下高防御装备……不对,是反过来——可以在被结算前换上高防装备、结算后换回输出装,用零成本换装规避数值。同类问题在技能换装(战斗中换技能槽重置冷却)上一并堵死,两条规则共用一个判定口径。

### 4.5 读档恢复

存档里装备实例全量序列化(InstId/ItemId/Equipped/词缀),读档恢复时**穿戴物先走 AddItem 进包,再走完整 Equip 流程**重建属性修改器——不直接写"已穿戴"状态。这样读档路径和玩家手动穿戴路径是同一条代码,不会出现"读档后词缀没生效"这类只在线上存档出现的问题。实例 Id 分配器读档时顶到 max+1,保证新掉落不会撞上旧实例的 Id。

### 4.6 物品 ID 段约定

| ID 段 | 类别 |
|-------|------|
| 1-99 | 神器(Artifact) |
| 200-299 | 货币(金币=200) |
| 300-999 | 书籍 |
| 1000-1999 | 消耗品 |
| 2000-2999 | 材料 |
| 5000-5999 | 装备类(对应装备表条目) |

ID 段不是摆设:使用物品系统按"1000-1999"识别消耗品效果类型,掉落系统、任务奖励按段做内容校验。段的纪律换来的是无数处 `if` 的省略。

## 六、系统关联

背包是经济域的枢纽,也是全项目扇出最广的系统之一:

**上游(谁往里塞/往外取)**:

- 掉落拾取系统——磁吸入包,是物品的主要水源;
- 剧情场景卡 ItemOps——对话引起背包变动(给钱/扣钱/给物),节点级与变量写回同帧原子执行;
- 任务奖励——交任务发奖走同一通道。

**下游(谁消费它)**:

- 装备系统——穿/卸,词缀转属性修改器;
- 合成/烹饪——扣材料、给产物;
- 商人经济——交易结算的扣款给货;
- 条件引擎——`item:1000 ≥ 1`、`gold ≥ 50` 两个谓词源直接读背包;
- UI——InventoryChangedEvent 驱动背包/装备面板刷新(事件驱动而非轮询,改一处全刷新)。

**联动回路**:掉落 → 背包 → 穿装变强 / 卖钱 → 更强地打怪 → 更好的掉落。这个循环转不得动,经济就死了;而循环里每一个箭头都过背包,这就是"唯一通道"的分量。

## 七、设计取舍记录

这一节记录当时为什么这么选,拆解系列里我个人认为最有价值的部分——**结论会过时,取舍逻辑不会**。

**取舍一:实例制取代"词缀外挂表"折中方案**。装备词缀系统 M1 时用过折中方案(词缀存在独立的映射结构里),M2 改成纯实例制。折中方案的问题:卖出、丢弃、存档三个路径都要特殊处理"映射结构同步",特殊路径越多 bug 面越大。实例制把词缀焊死在实例上,所有路径天然一致——代价是背包数据结构复杂了一档(两条轨),换来的是删掉一整类"映射失步"bug。

**取舍二:金币走背包而不是独立钱包字段**。独立钱包更快(一个 int),但交易、任务、剧情三条线都要各自写"扣钱给钱"的代码,而且任务系统想表达"奖励 3 金币 + 1 瓶药水"就得拼两种数据。金币物品化之后,奖励就是一个 ItemOp 列表,统一且可序列化。

**取舍三:容量只卡新条目**。有人会问"那 99 组堆叠不就等于无限容量?"——是的,而且这是有意的:容量压力应该来自"捡不捡得下新东西"的抉择(要不要为这件紫装腾格子),而不是"屯的家当怎么办"的仓管焦虑。前者是玩法,后者是 chores。

**取舍四:Param1 失配兜底而不是启动报错**。表侧数据债(部分装备 Param1 指向无效)是存量现实,启动即崩对开发期是灾难,静默兜底 + 首空位扫描让游戏在坏数据下仍可玩,同时把"槽位不精确"暴露给测试去修表。这是"数据债期间的过渡姿态",不是终态。
