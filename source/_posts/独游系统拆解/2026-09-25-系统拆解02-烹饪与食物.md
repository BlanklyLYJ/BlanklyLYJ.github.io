> 「游戏系统拆解」系列第二篇。上一篇拆了背包,这一篇拆烹饪与食物——一个很有代表性的案例:它几乎没有新增任何系统,而是把掉落、合成、属性修改器、营火交互四条现成管线拧成了一个"打猎采集 → 篝火烹饪 → 进食增益"的生存循环。怎么用最少的代码换一个完整的玩法体验,这一篇是个样板。

<!-- more -->

## 一、定位:生存循环的收尾一环

在整体循环图里,烹饪的位置是这样的:

```
探索打怪 ──掉落──► 食材(熏咸肉/苹果/蜂蜜)
                        │
                        ▼
             营火按 E(0.3s 起手) ──► 营火面板
                        │
                        ▼
             篝火烹饪(85% 成功率) ──失败──► 残渣(可卖)
                        │成功
                        ▼
                   熟食进背包
                        │
                        ▼
             火边进食 ──► 即时回血 + 限时六维 Buff(300s)
                        │
                        ▼
                  更强地探索打怪
```

它补上的是"食物"这个缺口。设计文档里对食物的定位从一开始就写死了分工:**血瓶 = 战斗即时救急(+30 HP),食物 = 战前预备的限时增益**。两者如果重叠——食物也能战斗中大口回血——血瓶的存在意义就没了,战斗中的决策(喝药还是走位)也会被"嗑食物"稀释掉。

## 二、五条体验铁则

调研阶段啃了旷野之息和 Valheim 的食物设计,五条铁则是整个系统的宪法,违反即 bug:

1. **烹饪必须发生在"火边"**。站点交互是仪式感的来源,不做"菜单里点点点"。旷野之息的锅、Valheim 的火塘,玩家对"围着火做饭"有肌肉记忆式的情感认知。落到实现:烹饪入口只挂在营火交互面板上,没有第二个入口;
2. **失败不没收材料价值**。失败产物是"残渣"(可卖给商人 1-2 金),惩罚是机会成本(这材料白采集了),不是资产毁灭(材料凭空消失)。挫败感设计中"损失资产"是最重的一档,烹饪这种高频行为不配用最重的惩罚;
3. **食物与血瓶分工**(上文);
4. **食物槽位上限 3 种**。Valheim 式的"吃 = 换 build":同时最多 3 种不同食物的增益共存,想上第 4 种必须等某个到期。同种食物重复进食 = 刷新时长,不叠加数值。这条规则把"吃饭"从无脑重复行为变成了选择:三个格子给谁;
5. ~~M1 配方全可见~~ → **食谱双通道发现制(2026-09-25 取代全可见)**:配方按 `Recipe_<Id>_Known` 变量控制可见性——**品尝学习**(吃陌生熟食学会做它,发现通道)+**任务传授**(Rewards.RecipeIds,教通道);未知配方不显示,面板只提示"还有 N 道未掌握"。初始已知=烤咸肉(开局底)。食谱书道具(第三通道)挂 M2。详见文末批注。

## 三、玩家体验走查

1. **白天打猎**:击杀野怪掉落熏咸肉、苹果、蜂蜜(已入测试怪的掉落表);采集系统是 M2,当前食材全靠打猎;
2. **入夜找营火**:营火是可交互物,走近按 E,0.3 秒起手动作(面向火堆 + 站定 + 白闪)——起手时间是交互系统统一的节奏,防"跑动中误触发";
3. **营火面板**:左边一列篝火配方(烤咸肉、蜂蜜苹果等 7 条),每行"产物名 + 材料行 + 烹饪按钮";材料够的绿色、缺的红色并显示缺口(如"熏咸肉 ×2(缺 1)");底部一个"睡觉到天亮"按钮——**烹饪和睡觉共用一个场所**,这是营火作为"夜间活动枢纽"的定位(夜间活动扩展见文末开放问题);
4. **点烹饪**:当帧结算(无进度条,篝火连续烹饪的节奏由玩家自己控制),滋滋音效 + 飘字"+1 烤咸肉";85% 概率成功,失败则是"烹饪失败……得到 残渣";
5. **同一面板直接吃**:配方行带"吃"按钮(拥有产物且产物有食物卡才显示)——"火边吃饭"与铁则 1 同场所。吃下去:咀嚼音效 + 飘字显示菜名和效果摘要;
6. **效果**:即时回血 8 点(clamp 到上限)+ 体魄 +2 持续 300 秒。进战斗后攻击结算直接吃到了这 2 点体魄的加成。

整条链路玩家感知到的"新东西"只有一个营火面板,其他全是既有系统在转:掉落表多了三种食材、合成系统多了一类配方、属性修改器多了一个来源。

## 四、核心规则全拆

### 4.1 食物效果卡:数据驱动的 JSON

每种熟食一张卡(FoodDef),编辑器目录扫描加载:

```json
{ "ItemId": 1090,
  "InstantHeal": 8,
  "FaithRestore": 0,
  "Buffs": [ { "StatName": "Character.Stats.Phy", "Value": 2, "Duration": 300 } ] }
```

三个字段各管一层:

- **InstantHeal**:即时回血,进背包管线前先结算;
- **FaithRestore**:回复信仰池——本作是低魔世界观,施法资源是"信仰"而非蓝条,所以存在"圣餐"型食物(吃了回信仰),这是世界观写进数值循环的一个小接口;
- **Buffs**:限时属性修改器列表,每条 = 属性全名 + 数值 + 时长。

加载期有一道**校验闸**:Buffs 里的 StatName 如果不是已注册属性,该条直接丢弃并警告。这是和装备词缀同一条纪律——**设计期拦截拼写错误,而不是运行期静默失效**。数值可以为负(M2 的"权衡型料理":+体魄 −移速的"重食"),留给未来的取舍设计。

还有一条 ~~M1 禁令值得展开:**食物 Buff 的属性域只允许六维**~~ → **2026-09-25 真源统一落地后 MaxHP/MoveSpeed 解禁**(DerivedAttrBridge 投影,配了即真实生效——血条/移速真实变化;六维仍是最常用安全域)。原禁令缘由保留为演进史:原因很硬:六维有真实的消费方(攻击公式 `Phy×2+5`、检定调整值),配上去就有效果;而 MaxHP、MoveSpeed 虽然在属性表里注册了,但 HealthComponent.Max 和 MoveComponent.Speed 是独立真源,属性修改器改不动它们——配了也只是监视器里数字好看,玩家什么也感受不到。**"看起来支持但其实无效"的配置项比不提供更恶劣**,所以直接禁掉,等属性真源统一(装备管线 M2)后再放开。

### 4.2 进食结算序:槽位检查先于消耗

结算顺序是这条系统里最容易被写错的点:

```
拥有该食物?──否──► 丢弃请求(什么都没发生)
   │是
有食物卡?──否──► 旧行为回落(1000-1999 段 +30 血,存档兼容)
   │有
槽位检查 CanEatMore?
   ├── 已持有同种食物 → 允许(这次进食=刷新时长)
   └── 新食物且活跃食物 ≥3 → 拒绝:飘字"吃太饱了",请求销毁,不消耗
   │通过
消耗物品 → 即时回血/回信仰 → Buff 逐条挂载 → 音效+飘字
```

**槽位检查在消耗之前**——吃太饱的判断失败时,食物不被吞掉。如果顺序反过来,玩家吃第 4 种食物会"既没吃到又扣了库存",这是最招骂的一类 bug。

"刷新不叠加"的实现:同种食物重复进食时,先把旧 Buff 按 SourceId 整批移除,再重新挂载——效果等于重置倒计时。而不是给旧 Buff 续时长(两种实现玩家感知相同,但前者复用属性系统的整批移除能力,零新代码)。

### 4.3 槽位的实现:不建计时层,借修改器当真源

活跃食物种类数怎么数?最直觉的做法是给实体加一个"食物槽位"组件,维护 3 个格子——但这引入了第二个真源:槽位组件和属性修改器列表各记一份"当前有哪些食物 Buff",两边失步又是 bug 面。

实际做法利用了 SourceId 命名空间:食物 Buff 的 SourceId = `900,000,000 + ItemId`(物品 Id 全表 <10000,这个段位与装备词缀的裸 itemId 永不冲突)。**活跃食物数 = 属性修改器列表里 SourceId ≥ 9 亿的去重计数**。Buff 到期由属性系统自动移除,槽位自然释放——不需要独立的计时层、不需要到期回调、读档时限时增益清空,槽位也自然归零。单一真源原则的一次干净落地。

### 4.4 烹饪流程:合成系统的表驱动改造

烹饪没有独立的"烹饪系统",它是合成系统(CraftSystem)的一类配方:

```
点「烹饪」→ 挂 CraftRequest{RecipeId, Station=CAMPFIRE} 到玩家实体
→ 下一帧结算,校验链:
    配方在表里存在?
    → Station 匹配?(防面板外伪造请求跨站合成——比如用篝火面板的请求
      触发只有铁砧才能做的锻造配方)
    → 材料齐备?(同材料多行聚合判定)
→ 扣材料 → 85% roll
    成功 → 产物入包(×max(1, ResultCount))
    失败 → 残渣入包(×1)
→ 产出入包失败(背包满)→ 退还全部材料 + 提示(不吞资产)
```

配置表里的配方按站点分段:篝火 1-7、厨房 101-103、半成品 201-204、药剂 401-403、熔炼 501-503、锻造 601-802。M1 只接了篝火(CAMPFIRE)——因为"厨房"需要实体载体(玛尔塔面包房),是 M2 的地图内容;但合成系统本身已支持任意 Station,接新站点 = 放一个新交互物 + 挂面板,零系统改动。

**防手速连点的双保险**:材料不足时按钮置灰不可点(UI 层),但系统侧仍保留"材料不足"守卫——因为面板刷新有延迟,跨帧连点时材料状态可能已变。UI 拦一道、系统拦一道,这是所有"按钮→请求"模式的标准姿势。

### 4.5 失败产物生态

失败不是一句"烹饪失败"就完了,每种合成类别有自己的失败产物:

| 类别 | 失败产物 |
|------|---------|
| 烹饪 | 残渣(2072) |
| 药剂 | 未知药水(2073) |
| 熔炼 | 矿渣(2074) |
| 锻造 | 粗制装备(各槽位一件,属性残次但能穿) |

这个生态的用意:失败产物是**可回收的残值**(残渣卖钱、未知药水喝了会有随机效果、粗制装备前期能凑合穿),配合铁则 2"失败不没收材料价值",把合成失败的体验从"纯损失"改成"次优结果"。

## 六、系统关联

**上游**:

- 掉落系统——食材来源(三种食材已入测试怪掉落表;M2 采集系统上线后扩充);
- 交互系统——营火(Camp 类型,按 E 0.3s 起手开面板);
- 合成系统——表驱动的烹饪执行底座;
- 配置表——H_合成表(TBRecipe)承载配方,`$Item[]` 跨表引用保证材料/产物 Id 可靠。

**下游**:

- 属性系统——食物 Buff 是属性修改器的一个来源(与装备词缀、技能 Buff 同管道);
- 信仰池——圣餐型食物的 FaithRestore;
- 背包——食材/产物/进餐全走背包通道。

**联动回路与挂点**:

- 战斗循环:战前吃 Buff → 属性高了 → 打得动更难的遭遇 → 掉更好的食材和材料;
- 随机事件系统预留了 OnCamp(营火挂点)——M3 的"宴席事件"(同伴围火吃饭触发夜话)从这里进;
- M2 的食谱发现制依托 WorldState 变量(`Recipe_X_Known`)+ 打听对话,把烹饪和叙事系统(见剧情篇)接起来。

## 七、设计取舍记录

**取舍一:不建独立食物计时层,借属性修改器当真源**。代价是"当前吃了什么"要靠 SourceId 段位反查,不如专门组件直白;换来的是零同步 bug、零到期回调、读档语义免费正确。凡是"已有真源能表达的,不建第二真源"——这条原则在这个项目里反复出现(剧情变量即存档、金币即物品),它值得成为个人准则。

**取舍二:食物 Buff 不入档**。读档后限时增益清空(与技能冷却清零同口径)。理由:限时状态的入档会显著增加存档复杂度(要存剩余时长、还要处理"离线时间流逝吗"的语义问题),而食物 Buff 的定位是"单次会话内的战前准备",跨会话保留它的收益配不上成本。

**取舍三:无烹饪进度演出**。点按钮当帧结算 + 音效,没有站在火边搅拌的动画。这是个诚实的取舍:M1 的目标是验证循环成立,演出是体验 polish,放 M2+。刻意记在这里,防止"没做"沉淀成"忘了"。

**取舍四:M1 配方全可见**。发现制(打听/试错录入)明明更有叙事味,为什么先做全可见?因为发现制的价值依赖"配方值得发现"——内容量上来之前,藏配方只是藏贫瘠。先全可见跑通循环,内容铺量后再加信息门槛,是"先验证再深化"的标准节奏。

| 问题 | 状态 |
|------|------|
| 食谱发现制(Recipe_X_Known + 打听口传) | M2 |

## 设计变更:食物词缀与新鲜度(2026-09-25 用户拍板,<mark>黄底=设计定稿待实现</mark>)

<mark>**食物逐件实例化**(用户拍板:逐件方案):有食物效果卡的道具逐件进入背包实例轨(同装备机制),一份一格——每一份烤肉都是独立个体,各自带词缀、各自过期。代价与收益:食物不再 99 个一堆,背包 20 格里一份占一格——**食物成为真实的资源决策**(烤多少、留多久、吃哪份)。</mark>

<mark>**两类食物词缀**:</mark>

| 词缀 | 来源 | 档位/示例 | 效果 |
|------|------|----------|------|
| <mark>厨艺词缀(制作侧)</mark> | <mark>烹饪完成瞬间 roll,受厨艺等级加成(联动第 15 篇职业)</mark> | <mark>厨艺精湛 +25% / 普通 1.0x / 火候欠佳 −15%</mark> | <mark>整餐效果乘数</mark> |
| <mark>新鲜度词缀(时间侧)</mark> | <mark>实例带 BornDay,每日结算(时间系统挂点,见第 26 篇)按保鲜期演化</mark> | <mark>新鲜 ×1.25(当日) / 正常 ×1.0 / 不新鲜 ×0.75 / 过期 ×0.5</mark> | <mark>整餐效果乘数,与厨艺词缀相乘</mark> |

<mark>保鲜期默认 3 游戏日(与商人补货/遭遇重生同节奏——世界三天一刷新的心智模型统一);过期档是否触发中毒效果留待实测裁定。效果结算:`ApplyItemEffect` 的数值 × 全部词缀乘数。</mark>

<mark>**实现批次**:随第 18 篇(词缀系统 2.0)一起落地——实例轨泛化是同一次改造。</mark>

## 验收批注(2026-09-25,第 02 篇封板)

**用户拍板**:①行囊进食降档方案**驳回**——<mark>进食场所无差异定则:在哪吃效果都一样,数值只由词缀决定;「火边仪式感」只约束烹饪制作(站点门控),不约束进食</mark>;②食谱发现制**双通道落地**——靠教+靠发现。

**实现**(RecipeKnowledge,2026-09-25):
