> 「游戏系统拆解」系列第四篇,拆剧情系统。这篇覆盖叙事域的五个咬合件:场景卡(剧情的容器)、WorldState(叙事状态层)、全局条件引擎(唯一的判定入口)、打听式任务(知识分级)、DC 检定演出。一句话先立住整个域的设计观:**剧情是数据不是代码,知识本身就是玩法**。

<!-- more -->

## 一、定位:叙事域要解的三个问题

1. **内容如何被批量生产**——如果每段对话都是一段代码,内容量永远上不去。答案:场景卡 JSON,编剧工具链直通,写卡的人不碰代码;
2. **世界的记忆放在哪**——"玩家帮过乞儿"这个事实,谁记着?记在哪?答案:WorldState 变量注册表,变量即存档;
3. **判定如何不被写成意大利面**——"夜间 + 好感 ≥20 + 完成过某任务才能触发这段对话",这类判定会散落在所有系统里。答案:全局条件引擎,12 个谓词源,全项目唯一求值入口,禁止私写判定。

## 二、场景卡:对话内容的统一容器

一段剧情 = 一张 JSON 卡,结构四件套:

```
节点(文本/演出)──► 选择点(选项带条件过滤)──► 分支
                                        │
                 结束写回 WorldState 变量 ◄──┘
```

以演示卡"面包房的烧伤"(StRose_N01)为例:6 个节点、2 个选择点、4 条分支,走完后写回 `StRoseN01Done=TRUE`——再按 E 不会重复触发,因为进卡前置有条件引擎把关。

**选项级条件过滤**是分支深度的控制阀:选项不满足条件的**隐藏或灰显**,而不是点了之后告诉你"现在不行"。玩家在对话里看到的每一个可选项都是当前真实可达的,选择的负担集中在"选哪个"而不是"哪个能点"。

**ItemOps 物质通道**让对话能引起背包变动:

```
节点/选项上挂 ItemOp{ Op: TakeGold, Amount: 3 }
  ├── GiveItem / TakeItem / GiveGold / TakeGold 四种操作
  ├── 检定卡只在成功侧执行(失败给奖励不合直觉)
  └── 与变量写回同帧原子成对——"扣 3 金"和"写 BeggarHelped=1"
      不存在中间态,读档不会读到"扣了钱没记情"的存档
```

失败语义是"跳过 + 警告"而不是硬报错:门控责任在卡的前置条件(比如 `gold ≥ 3` 才显示这个选项),通道本身只管执行——**通道不做决策,决策在数据里**。

**检定演出**(PlayCheckRoll)是最近打磨的一块:检定结果不再瞬时显示,而是 1d20 骰面滚动约 0.7 秒(8 步、间隔渐增的减速感)→ 定格完整算式 `1d20(14)+2=16 → 成功`。滚动期锁死继续按钮,防止剧透式跳过。这是从 BG3 抄的节奏:**骰子滚动的悬念半秒就是检定玩法的全部多巴胺**,瞬显等于把抽奖直接改成开奖公告。

## 三、WorldState:变量即存档

叙事状态的存储走一个全局单例注册表,三条铁律:

1. **未注册变量拒绝写入**。变量必须先登记才能用,拼错变量名立刻警告——用设计纪律换数据安全。剧情变量名的拼错是叙事 bug 的第一大来源(`BegarHelped` vs `BeggarHelped`,写错了游戏不炸,但那段剧情永远判定失败,还查不出来);
2. **变量三族命名**:任务态 `Quest_*`、事件冷却 `EV_*`、遭遇重生 `Enc_*`——三族全部直接随存档,**叙事系统零持久层代码**;
3. **变更发事件**(WorldStateChangedEvent),调试面板和条件刷新都订阅它。

这套设计的本质:**把"世界的记忆"做成一张扁平的键值表,并且让这张表天然就是存档**。没有剧情进度树、没有章节标记、没有任务日志结构——所有叙事状态都是变量,多周目想继承什么、剧情想检查什么,都归结为对这张表的操作。

## 四、全局条件引擎:全项目唯一的"是否"入口

这个系统的设计动机是一次收编:此前项目里有 4 套各自为政的判定逻辑(剧情卡评估器、GOAP 谓词、商店定价内嵌判断、时间事件检查),每套都有自己的语法和 bug。收编成一个引擎后:

**数据模型**:一行 = `{Source, Key, Op, Value, OrNext}`。行间默认 AND,行尾勾选 OrNext 连排构成 OR 组,可表达 `(A∨B)∧C∧(D∨E∨F)`;空组恒真(不配条件 = 无门槛);**源或键不存在 → false + 警告**(引用错误尽早暴露,而不是静默不触发)。

**12 个谓词源**是表达力的全部疆域:

| 源 | 语义 | 示例 |
|----|------|------|
| var | WorldState 变量 | StRoseN01Done == 1 |
| attr | 玩家六维 | Wil ≥ 12 |
| rep | 阵营声望 | Rep.StRose.Fame ≥ 30 |
| time | 游戏时间 | Hour in 20-5 |
| loc | 地理位置 | Near=面包房@8 |
| quest | 任务状态 | QM_xxx.Status == DONE_A |
| gold | 金币 | gold ≥ 50 |
| item | 物品持有 | item:1000 ≥ 1 |
| weather | 天气 | Rain.Intensity ≥ 40 |
| flag | GOAP 谓词反读 | 欧文:HasGold |
| party | 队伍成员 | party:Viktor == 1 |

注意 flag 源——它能读 GOAP NPC 的内心状态(上一篇讲过的反向桥)。12 个源等于把整个游戏世界的实时状态都翻译成了"条件语言",剧情门控、事件触发、GOAP 感知、声望门槛,说的是同一种话。

**工具链是半个系统**:图编辑器里的条件面板(Source 下拉 → Key 联动 → Op → 行尾 ∨ 勾选)服务剧情和事件两个消费方;Play 模式的条件求值器调试窗逐行红绿实时显示——**设计师排查门控问题不进游戏、不看日志**。条件系统的用户是设计师不是程序员,工具链的完成度决定系统的真实产能。

**一个刻意的设计克制**:OrNext 只做行级 OR(Bethesda Creation Kit 同款),不引入嵌套树/括号。行级 OR 覆盖了 95% 的真实需求,而嵌套树的复杂度(可视化、序列化、心智负担)会吃掉整个工具链。剩下 5% 的复杂条件,用"在 WorldState 里落一个中间变量"解决——布尔逻辑不够时,加变量,不加语法。

## 五、打听式任务:任务不是接来的

传统任务范式的流水线:接任务(NPC 头顶感叹号)→ 目标列表 → 回来交任务。这个范式的隐藏假设是**任务信息是免费的**——玩家和角色总是知道要做什么、去哪做。

打听式任务把这个假设砸了,换成四条核心理念:

1. **发现即记录**:搭话答应、旁听路人、主动打听,任何信息获取都记进日志谱,做不做随玩家(巫师 3"选择不标示"哲学——记下了,但选择权在你);
2. **知识分级**:`KnowObj`(知道做什么:UNKNOWN→PARTIAL→FULL)和 `KnowLoc`(知道在哪:UNKNOWN→KNOWN)**独立获取、独立存储**。知识不全则指引不全——只知道地点,导航 HUD 只带到那个地区;只知道目标,HUD 显示"?"。**知识状态直接决定 UI 的信息量,而不是装饰它**;
3. **追踪解锁交互**:同一时间全局只能追踪一条任务,追踪中的任务才解锁"打听"对话选项和导航 HUD。未追踪的任务问不出情报——玩家的注意力一次一条线,系统帮玩家管注意力;
4. **多结局交还**:交任务时的对话分流复用 DC 检定 → 不同 `DONE_<ending>` 写回 → 日志按结局归档。

**任务卡数据模型**与剧情卡同构同管线(这是"剧情是数据"的复利):QuestId、发现场景列表、旁听场景列表、**KnowledgePool**(打听可泄露的知识碎片,随机抽取——同一个 NPC 两次打听说的不完全一样)、目标(go/talk/kill 三类)、多结局、交还场景、奖励(可含技能习得)、前置条件(条件引擎)。任务状态变量走 WorldState 镜像——**存档系统又一次零改动**。

**交互流走一遍**:玩家在酒馆旁听到"北边狼群袭扰羊圈"(旁听也是一等公民,原子动作 listen 与 gather/kill/go/deliver 并列)→ 日志谱记下,处于 UNKNOWN 状态 → 追踪该任务 → 找本地猎人"打听:狼患" → 猎人泄露一个知识碎片(方向)→ KnowledgePool 抽取,`KnowLoc` 推进 → HUD 八方位导航点亮 → 到达、清剿 → 回城交还,检定口才可以多要报酬 → 结局写回。

这条流水线里没有一处"NPC 头顶感叹号"。信息是玩家**主动挣来的**,挣的过程(打听、旁听)本身就是玩法——这就是"信息即玩法"支柱的落地形态。

## 六、数值与参数速查

| 项 | 数值 |
|----|------|
| 检定骰 | 1d20 + 属性调整值 vs DC |
| 检定演出 | ~0.7s,8 步减速滚动 |
| 自动决策窗口 | 1.2s(对话无操作时) |
| 谈天冷却 | 单 NPC 每游戏日 1 次(防刷) |
| 打听条件 | Region 匹配 + 追踪任务有未获知识 |
| go 目标判定 | 距地标 ≤8m,0.5s 轮询(仅追踪任务) |

## 七、系统关联

叙事域内部是严格的分层供血:场景卡/任务卡(内容层)→ WorldState(状态层)→ 条件引擎(判定层)。对外:

**上游(消费谁的数据)**:背包金币/物品(gold/item 源)、属性(attr 源)、声望(rep 源)、时间(time 源)、地理注册表(loc 源)、天气、GOAP(flag 源)、队伍(party 源)——**条件引擎把半个项目都变成了叙事的原材料**。

**下游(谁消费叙事的产出)**:任务技能奖励 → 技能习得;ItemOps → 背包;场景卡结局变量 → 后续内容门控、声望系统(AttrDelta 通道);随机事件系统复用整套卡管线(SceneId 引用);睡觉触发的夜间故事(M2)同管线。

**枢纽地位**:条件引擎是叙事域第一枢纽,扇入 12 源、扇出 5 个消费方。动它之前先数一遍这张表。

## 八、设计取舍记录

**取舍一:扁平变量表,不做剧情进度树**。进度树(章节→场景→节点)看起来更"结构化",但它的刚性会在多周目、POV 叙事、随机事件交叉时碎掉——树要求单一主线,而本作的叙事野心恰恰是多线交织。扁平表 + 条件引擎的组合,表达力是"任意布尔条件下的任意内容可见性",这才是开放世界叙事的真实形状。

**取舍二:行级 OR,不做嵌套树**(上文已述)——语法复杂度换变量技巧,永远是赚的。

**取舍三:知识分级只有两轴,不做知识图谱**。设计期间考虑过"知识点之间有关联(知道 A 才能理解 B)"的图谱方案,否决。知识图谱的表达力对叙事深度确有增益,但 UI 呈现(图谱怎么给玩家看?)和信息管理(玩家心智负担)都过重。两轴分级(做什么/在哪)覆盖了"指引不全"的核心体验,复杂度只有图谱的十分之一。**先问"这个深度玩家感知得到吗",感知不到的深度就是自嗨**。

**取舍四:追踪唯一,不做并行多任务导航**。现代 3A 的趋势是"任意任务并行追踪+罗盘塞满图标",本作反着来。理由:打听式任务的信息本身就是稀缺资源,并行追踪会稀释"一次追一条线"的专注感,HUD 八方位导航+距离读数的简洁形态也撑不住多线同屏。代价是玩家切换追踪的频率变高——这是用便利性换专注度的交易,是否符合口味,留给实测。
